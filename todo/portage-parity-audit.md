# Portage parity audit (2026-10-26)

Source audit of em against gentoo/portage master `f13a45f3f` (cloned at ../portage), one finder per
subsystem, each finding checked by an independent refuting agent (165 confirmed, 4 refuted).
Duplicates across subsystems are kept; the live harness (`test-scripts/parity/`) confirms some below.
Status: open unless marked.


## atom-version

- **high** missing: Wildcard atoms (*/*, cat/*, */pkg, =cat/pkg-*x*) unsupported; lines that use them in /etc/portage are dropped without a warning
  em `portage-resolve/src/use_env.rs:541`, portage `lib/portage/package/ebuild/_config/UseManager.py:344 (also KeywordsManager.py:81, MaskManager.py:218, LicenseManager.py:40, dep/__init__.py:2026-2056 and :334 _get_atom_wildcard_re)`
  Fix: Add an extended-atom type (glob on category/package, plus the `=cat/pkg-*ver*` substring form) in portage-atom. Have the user-config loaders accept it and match it against the cpn, like portage's ExtendedAtomDict; warn on lines that still fail to parse. Verifier: The package.env loader is portage-repo/src/package_env.rs:79, not portage-resolve. load_package_license also loads package.properties and package.accept_restrict, so those files are affected too. load_dep_list (package.mask/unmask) is affected the same way.
- **high** bug: Pubgrub glob range [V, bump(V)) disagrees with glob_matches: drops 1.2_rc1, admits 1.3_alpha and 1.2.1 for a letter pattern
  em `portage-atom-pubgrub/src/version_set.rs:142`, portage `lib/portage/dep/__init__.py:3103-3117`
  Fix: Build the =* set from the same predicate as glob_matches (filter the candidate versions), or set the lower bound below all suffixes (V with _alpha0 minus epsilon) and the upper bound below bump(V)_alpha, honouring the letter. Then fix glob_matches itself per the previous finding. Verifier: One part of the fix sketch needs correcting. A range with an epsilon lower bound cannot match portage exactly, because a string-prefix match is not one contiguous interval. With a letter pattern, for example, 1.2a and 1.2a_p1 match, while 1.2b and 1.2.1 sit in between and do not. The safest fix is to build the `=*` set as the union of singletons of the candidate versions for which `glob_matches` returns true, once `glob_matches` itself follows portage's prefix semantics.
- **medium** bug: =V* glob ignores the pattern's suffixes and revision, so =pkg-1.2_rc* matches 1.2 final and 1.2.5
  em `portage-atom/src/version.rs:427`, portage `lib/portage/dep/__init__.py:3071-3117`
  Fix: Implement =* as portage does: render the candidate PVR (lstrip leading zeros of the first component), check that it starts with the pattern string, then apply the part-boundary next-character rule. Or compare the pattern's suffix list and revision as a prefix too. Verifier: Severity is medium rather than high. Glob patterns with suffixes or revisions (`=pkg-X_rc*`, `=pkg-X-rN*`) are uncommon in profiles and user config, but where they are used, em over-matches: it can mask or keyword-accept final releases and other revisions. The 1.0* vs 1.00 case is a minor edge case. The simplest fix is to match portage: compare the pattern as a literal prefix of the candidate's rendered PVR (first component's leading zeros stripped), then apply the boundary rule.
- **medium** bug: `::repo` must follow `[use]` in em; portage requires `:slot::repo[use]`
  em `portage-atom/src/dep.rs:335`, portage `lib/portage/dep/__init__.py:303-324`
  Fix: In parse_dep, parse `::repo` before the USE-dep brackets (optionally still accept the old order), and switch Dep's Display to slot, repo, use. Verifier: The claim is accurate. Em's Display also emits `[use]::repo`, so any atom em writes out with both parts (for example to a config file or the world file) cannot be read by real portage. A fix should accept portage's order. Whether em should keep accepting the old order is a choice, since portage rejects it.
- **medium** bug: DepEntry::parse panics (index out of bounds) when the dependency string ends with `?`
  em `portage-atom/src/dep_entry.rs:405`, portage `lib/portage/dep/__init__.py:1000`
  Fix: Use `bytes.get(i + 1).is_some_and(u8::is_ascii_whitespace)` in place of the direct index. Verifier: The trigger needs `?` as the very last byte of the remaining input, with no trailing whitespace. md5-cache values are stored without trailing whitespace, so that case is realistic. The fix sketch is right: `bytes.get(i + 1).is_some_and(u8::is_ascii_whitespace)`.
- **medium** divergence: USE dep on a flag missing from the target's IUSE, with no (+)/(-) default, is treated as disabled instead of not matching
  em `portage-atom-pubgrub/src/validate.rs:599`, portage `lib/portage/dep/__init__.py:3215-3217`
  Fix: When the flag is absent from the target's IUSE (including IUSE_EFFECTIVE implicit flags) and ud.default is None, treat the candidate as not matching the atom rather than defaulting the flag to Disabled. Verifier: The live em code is portage-atom-pubgrub/src/provider/post_solve.rs:357 (effective_flag_new) and :126-130. validate.rs:599 (resolve_flag_state, called only from check_use_deps) is used only by tests. For the fix, iuse should be checked against IUSE_EFFECTIVE (implicit/USE_EXPAND_IMPLICIT flags), so implicit flags are not falsely rejected. Candidates with missing IUSE also need to be excluded before or during the solve, not only flagged afterwards, to match portage's backtracking to another version that has the flag.
- **low** divergence: Operator-less versioned atoms (cat/pkg-1.0) parse as valid, then mean `=` in the solver and match nothing in mask/USE matching
  em `portage-atom/src/dep.rs:278`, portage `lib/portage/dep/__init__.py:2100`
  Fix: Reject a version without an operator in parse_dep (as portage and PMS do). Callers that want the `=` shorthand for CLI targets should add it explicitly. Verifier: Severity is lower than claimed. In package.mask, package.use, package.env and the like, the user-visible result is about the same as portage's: the line has no effect, because em's matchers return false and portage drops the invalid atom. The only difference users see there is that em gives no "Invalid atom" warning. The `=` meaning only applies inside the solver bridges, i.e. DEPEND strings and set or target atoms that reach convert_atom. Ebuilds in the tree do not contain such atoms (pkgcheck/repoman reject them). In practice the user-facing gap is the missing warning plus the internal inconsistency (the solver says `=`, the matchers say "no match"). The suggested fix stands: reject a version with no operator in parse_dep and add `=` explicitly where a CLI shorthand is wanted.
- **low** missing: Build-id atoms (=cat/pkg-1.0-r1-3) cannot be parsed
  em `portage-atom/src/cpv.rs:135`, portage `lib/portage/dep/__init__.py:2063-2077 (match at :3061-3064)`
  Fix: After an `=` operator, accept a trailing `-<digits>` (no leading zero) as Dep.build_id and match it against the binpkg BUILD_ID. Verifier: The claim is right for versions that contain a dot (=app-misc/foo-1.0-3 is rejected outright). An all-integer version is worse: parse_package never checks the PMS rule that a package name must not end in a hyphen plus a valid version. So =app-misc/foo-1-3 parses without error as package "foo-1" at version "3". It then matches nothing, and the user gets "no match" rather than an invalid-atom error.
- **low** bug: Resolvo bridge inverts `[!flag?]`: requires the dep's flag enabled when the parent's is off
  em `portage-atom-resolvo/src/provider.rs:1525`, portage `lib/portage/dep/__init__.py:1214-1215 (conditional 'disabled' -> evaluated as !flag? ( pkg[-flag] ))`
  Fix: Push (flag, false) for ConditionalInverse, and fix the doc comment to say "must be disabled". Verifier: Fix: in resolvo resolve_use_deps, ConditionalInverse should push (flag, false) when the parent's flag is off. Also change the doc comment in use_dep.rs:46-47 to say "must be disabled". PMS 8.3.4 is the right section reference (the comment in post_solve.rs cites 8.2.6.4).
- **low** divergence: USE-dep list validation is looser than portage: [], [a,], conflicting defaults accepted
  em `portage-atom/src/use_dep.rs:233`, portage `lib/portage/dep/__init__.py:1196-1230`
  Fix: Require at least one item, drop the trailing opt(','), and reject a flag that appears with differing or mixed default annotations. Verifier: Correction to the claim: portage rejects only mixed default annotations for one flag (or a default on one token and none on another). It does not reject a flag that appears more than once with the same annotation. So the fix should match that rule and not reject every repeated flag. The em tests deliberately accept `[]` and the trailing comma ("Issue 1"/"Issue 4"), so tightening the parser means changing those tests. Impact is low: em's parser is only more permissive and accepts no extra valid atoms.
- **low** divergence: `:slot*` slot dep accepted; portage rejects a named slot with the * operator
  em `portage-atom/src/slot.rs:264`, portage `lib/portage/dep/__init__.py:2124-2125`
  Fix: Allow only `=` after a named slot in parse_slot_dep; keep `*` for the bare `:*` form. Verifier: This is a parser that accepts too much, which belongs with the items in todo/pms-parser-lenient.md (PMS 8.3.3). It is not an EAPI-gated difference. Fix: in parse_slot_dep, allow only `=` after a named slot.
- **low** divergence: Atom parsing has no EAPI gating (::repo, use-dep defaults, slot operators, !! accepted in any EAPI)
  em `portage-atom/src/dep.rs:337`, portage `lib/portage/dep/__init__.py:1985-1988 and :2154-2177`
  Fix: Thread the EAPI into DepEntry parsing for ebuild metadata and reject features the EAPI lacks; keep the unrestricted parse for user config and CLI. Verifier: Known item, documented in todo/pms-parser-lenient.md (known=true). The `::repo`-in-ebuild-metadata case (EAPI 0-8) is not in that note, and it is the most plausible one in an overlay. The others (use defaults in EAPI 3, `!!` in EAPI 0-1) affect only obsolete EAPIs. It is only user-visible when a broken overlay ebuild is involved: portage masks it as invalid metadata, while em quietly resolves it. Severity stays low.

## binpkg

- **high** bug: quickpkg packs every directory as mode 0700 (umask 077 applied to staging mkdir)
  em `portage-cli/src/quickpkg.rs:307`, portage `lib/portage/gpkg.py:1491`
  Fix: After creating each staged dir, copy the live dir's mode/uid/gid with set_permissions/chown (or build the tar from CONTENTS with the live lstat values, as portage does). Verifier: The claim about em's own `em -K` is not accurate. em's merge, portage-cli/src/ebuild/mod.rs:3053-3061 (dir()), uses create_dir_all under the process umask plus preserve_owner (lchown only). It ignores the image dir's mode, so em -K installs these dirs as about 0755 and hides the bug locally. That is a separate divergence: em never applies image dir modes such as 0750 or setgid. The user-visible damage is for portage consumers of em-built binpkgs, and in the archive itself: tar -tv shows drwx------, and dir ownership like /var/lib/foo owned by foo:foo is lost and replaced by the quickpkg runner's uid. Fix: copy lstat mode, uid, gid and mtime of each live dir onto the staged dir, or build the image tar from CONTENTS with the live lstat values as portage does.
- **high** bug: CHOST gate bypassed for portage-written Packages indexes (header-inherited CHOST ignored)
  em `portage-binpkg/src/index.rs:338`, portage `lib/portage/getbinpkg.py:146`
  Fix: In parse_packages_entries, parse the header and fill a missing per-entry CHOST (and REPO) from it before building BinpkgEntry. Verifier: The claim holds. It also hits the local PKGDIR fast path (BinpkgIndex::open -> parse_packages_entries), not only -g remote indexes. To fix it, have parse_packages_entries (or its callers) parse the header and fill a missing per-entry CHOST (and repository) from it, as getbinpkg.py readBody does. The test at index.rs:1213, which asserts that the header CHOST must not leak, would then have to change: it guards against a block-splitting bug and should not block a deliberate inheritance from the header.
- **medium** bug: Binpkg USE reuse check ignores IUSE changes in the current ebuild
  em `portage-binpkg/src/index.rs:539`, portage `lib/_emerge/depgraph.py:3393`
  Fix: Pass the planned ebuild's IUSE into find_reusable and reject when the IUSE symmetric difference (minus forced/masked flags) is non-empty, then compare USE∩IUSE as today. Verifier: Portage rejects the binpkg for any IUSE change outside force/mask, even when the newly added flag ends up disabled. The trigger is wider than the "+b enabled" case the claim gives. Under -K (usepkgonly) and --use-oldpkg, portage uses the binpkg's own IUSE as cur_iuse, so there em's behaviour matches. I lowered severity to medium because the gap only appears when IUSE changes in place without a revbump. In that case it still silently installs a stale binary.
- **medium** bug: quickpkg drops protected configs entirely and installs a stray /.quickpkg-config-omitted file
  em `portage-cli/src/quickpkg.rs:231`, portage `lib/portage/gpkg.py:1384`
  Fix: Replace each excluded protected file in the staged image with the one-line placeholder at the same path, keeping the file's mode and owner, and drop the root-level marker file. Verifier: The claimed effects follow directly from the code. The protected paths are missing from the binpkg, so they are also missing from the CONTENTS written when it is installed. A stray `/.quickpkg-config-omitted` is merged and recorded instead, and two such binpkgs collide on it. The fix is as sketched: stage each protected file as the placeholder at its own path, keeping its stat metadata, and drop the root marker.
- **medium** bug: Downloaded remote binpkgs not checked against the index SIZE/MD5/SHA1; the cache is keyed only by basename
  em `portage-cli/src/merge/mod.rs:1256`, portage `lib/_emerge/BinpkgVerifier.py:27`
  Fix: Carry SIZE/SHA1/MD5 from the index entry, verify the downloaded file before use, and key the cache by binhost plus PATH (or download into PKGDIR at PATH). Verifier: Your claim is accurate. The GPKG's internal Manifest and the optional signature check only prove the container is internally consistent. Neither ties the file to the index entry that was chosen.
- **medium** divergence: binrepos.conf [DEFAULT] verify-signature = true (shipped by portage) is ignored (known: [DEFAULT] inheritance is listed as a deliberate simplification in portage-cli/src/binpkg.rs:343 and todo/PENDING.md:1039 ("no configured value observed in practice needs either"), but portage's own shipped file needs it.)
  em `portage-cli/src/binpkg.rs:413`, portage `cnf/binrepos.conf:1`
  Fix: In combine_binhosts, fall back to sections["DEFAULT"] for each key a named section does not set (at least verify-signature and frozen). Verifier: Known simplification (binpkg.rs:343, todo/PENDING.md:1039), but the justification there is wrong because portage's stock cnf/binrepos.conf relies on [DEFAULT]. Fix: in combine_binhosts, build each section's effective map as sections["DEFAULT"] overlaid with the section's own keys. Apply it to named sections only, not the PORTAGE_BINHOST implicit entries.
- **medium** divergence: -K/--usepkgonly still requires USE to match exactly; portage installs the binpkg as built

  em `portage-binpkg/src/index.rs:491`, portage `lib/_emerge/depgraph.py:8344`

  em `portage-cli/src/quickpkg.rs:318`, portage `lib/portage/gpkg.py:1491`
